## 3. Product principles

1. **Audit first:** L1 only observes; it never silently changes OS configuration.
2. **Independent agent:** audit must work offline, without a running GUI or reachable server, using a locally validated policy.
3. **Server-owned desired policy:** checks are enabled, disabled and parameterized centrally per endpoint or group; offline fallback uses the last trusted applied policy.
4. **Two-sided custom-check registration:** custom executable/script must be authorized in server policy and registered locally with matching identity, version and content digest.
5. **Built-in and custom checks share one result contract**, but not necessarily the same trust level.
6. **Least privilege:** normal agent runs with minimal privileges; privileged inspection or remediation uses a narrow, authenticated helper only when necessary.
7. **No remote shell:** server cannot execute arbitrary commands on endpoints. Remediation uses an explicit, typed allowlist of operations.
8. **Evidence over assertion:** distinguish a verified observation from an untrusted script's claim. Do not treat a reported PASS as a cryptographic guarantee of machine integrity.
9. **Platform-specific implementations, platform-neutral semantics:** Fedora, Ubuntu, Arch Linux, Windows and macOS must map to the same logical controls where feasible.
10. **Measurable milestones:** every milestone has demonstrable acceptance tests; avoid implementing future levels prematurely.

## 4. Deployment and components

### 4.1 Server (`BaradWatchU-Server`)

- Linux executable/service with an embedded or co-hosted Angular web dashboard.
- API for enrollment, policy assignment, audit ingestion, evidence retrieval, inventory and reports.
- Stores historical policy versions, check results, timestamps and device identities.
- Generates machine-readable JSON/CSV and human-readable PDF reports; audit trails must include relevant policy/check versions.
- Supports authentication, role-based authorization, tenant/organizational separation if later required, TLS and audit logs.
- Bootstrap technology baseline: **Rust + Axum**, Angular. Server MVP uses SQLite for explicit identity, trusted Clients and issuer/sub administrators; received report history scoped by requesting operator in the same SQLite database (alignment milestone). PostgreSQL remains future scope.
- Deployment must not require AWS or any other public cloud; on-premises operation is supported.
- Linux distribution channels: source installer, Arch `pacman`, Debian/Ubuntu `.deb`, Fedora `.rpm`. Source installation is distinct from package-manager ownership; source uninstallation must never remove package-owned files.
- Planned system locations: executable `/usr/bin` (packages) or `/usr/local/bin` (source), web assets `/usr/share/baradwatchu-server/web`, configuration `/etc/baradwatchu/server`, persistent state `/var/lib/baradwatchu/server`. L0.1.1 source install writes only executable/assets/manifest and creates no service/config/data.
- Server systemd packaging/service lifecycle is deferred; local installation is a manually launched development binary. Startup validates an IP:port address from `BARADWATCHU_SERVER_ADDR`, enables Tokio I/O/time drivers, reports failures with exit 1 (CLI misuse: 2), and drains connections on SIGINT/SIGTERM. The HTTP router and configuration are independent of process startup for tests.

### 4.2 Agent (`BaradWatchU-Client`)

- A **background OS service**, independent of the user interface:
  - Linux: `systemd` system service (Ubuntu, Fedora, Arch Linux).
  - Windows: Windows Service.
  - macOS: `launchd` LaunchDaemon.
- Current implementation: Rust bootstrap, L1.1 CP1 standalone audit (§5.3), CP2 local policies/Fedora hardening (§5.4), CP3 native Arch/shared Linux inspection (§5.5), and CP4 Linux security baseline (§5.6). Background lifecycle, Python/custom checks and signed-policy handling remain deferred.
- Provides device inventory, policy validation, audit execution, evidence collection, secure server sync and offline JSON output.
- Future responsibilities: scheduler, notification dispatch, typed privileged remediation and post-remediation audit.
- Never rely on an open user session for background checks or server communications.
- Linux distribution channels: source installer, Arch `pacman`, Debian/Ubuntu `.deb`, Fedora `.rpm`; Windows client `setup.exe`; macOS client `.dmg`. A channel is supported only after its actual artifact passes clean install/upgrade/uninstall tests on its target OS.
- Planned Linux system locations: executable `/usr/bin` (packages) or `/usr/local/bin` (source), UI assets `/usr/share/baradwatchu-client/web`, configuration `/etc/baradwatchu/client`, persistent identity/audit/custom-check state `/var/lib/baradwatchu/client`. Source installer writes only executable/assets/manifest and does not install a system service.
- User-local paths are development-only: executable under `~/.local/bin`, future configuration under `~/.config/baradwatchu/client`, data under `~/.local/share/baradwatchu/client`. A user-local copy is not a system agent and provides no privileged/system-wide auditing.
- Linux package service ownership will use a systemd system unit. Windows service registration requires administrator authorization and a signed package; macOS uses an admin-authorized `launchd` LaunchDaemon and signed/notarized distribution. Service lifecycle integration is deferred until explicit lifecycle tests exist.

### 4.3 Local client UI

- Angular UI launched by a desktop shortcut/application launcher.
- Read-only status, local audit results and history initially; it is **not** the process responsible for background notifications, scheduling or remediation.
- It may open in a local browser or a desktop shell; **Tauri is optional**, not a requirement.
- Use authenticated local IPC or a carefully secured loopback interface; localhost alone is not an authorization boundary. **Implemented (M7 tray):** random per-session token required on every `/api/` call (header `X-BaradWatchU-Token`), Host check, Origin + JSON content type for mutations; token delivered via a 0600 launcher file in `$XDG_RUNTIME_DIR/baradwatchu/`, never on a command line; one dashboard per user session is reused.
- UI runs without administrative privileges and must not access device secrets.
- Desktop viewer launcher/package is separate from the background service lifecycle. Development `npm start` runs on loopback: Server UI port 4200, Client UI port 4201. It neither starts nor controls a Rust process. Select Node 20 >=20.11.1 using `web/.nvmrc`; preflight and npm engine checks reject incompatible Node versions.

### 4.4 Product versioning and distribution (L0.1.1)

The product version follows Semantic Versioning (`MAJOR.MINOR.PATCH`). Server and Client have independent release lifecycles; each starts at `0.0.1`. Each repository has one authoritative Rust workspace version in root `Cargo.toml` (`[workspace.package].version`); crate versions inherit it. Rust binaries expose `--version`/`-V` and `--help`/`-h`, and version reporting must not start a server, agent service, browser or privileged component. Angular package/UI versions and package metadata must be generated or synchronized from that repository's authoritative version. Product version is not a protocol/schema version; wire compatibility versions remain separately defined.

Installer requirements:

- Linux source `install.sh` in both repositories supports `--help`, `--missing-deps`, `--dry-run`, `--no-build`, `--build-only`, `--local`, `--uninstall`, `--prefix=DIR`, and optionally `--build-dir=DIR`; invalid args return 2, execution/validation errors 1, success 0.
- Read-only dependency audit recognizes Arch, Fedora, Debian and Ubuntu via `/etc/os-release` `ID`/`ID_LIKE`, checks build/runtime versions and local Angular npm dependencies, separates optional tools, and prints package-manager/project-dependency-specific suggestions. It may load an existing nvm and select the version in `web/.nvmrc` for the installer process; it does not install nvm or download Node automatically. It never installs system dependencies.
- Release builds run unprivileged in a marked project cache using Cargo `--locked` and npm `ci` against an isolated Angular source copy; checkout node_modules is preserved. npm/node-gyp caches and logs stay under the build directory. Cache format v2 records source origin/fingerprint (including install.sh and lockfiles), platform, product version, artifact digest and build-host glibc. `--no-build` verifies content and requires glibc at least as new as the build host without executing cached binaries. Legacy v1 caches require rebuilding. Stage artifacts before installation; a normal-user invocation requests sudo only for protected-prefix file installation, never for building. It performs no automatic service action.
- Source install/uninstall is manifest-owned and hash-checked; refuse files owned by `pacman`, `dpkg`/`apt` or `rpm`/`dnf`, and refuse modified files. Preserve configuration, enrollment identity/keys, audit history and custom checks by default. Do not mix source and package-manager ownership.
- User-local installation is explicitly development-only, with no system service or privileged checks. System-wide installation must not silently create a production service. Agent systemd lifecycle and desktop viewer launcher are separate.
- `--dry-run` shows version, scope, prefix, cache, dependencies and operations without changing files or services. Do not claim transactional rollback unless verified.
- Distribution targets are source install, Arch `pacman`, Debian/Ubuntu `.deb`, Fedora `.rpm`; Client additionally targets Windows `setup.exe` and macOS `.dmg`. Release formats, service registration, signing/notarization and OS-native uninstallation remain deferred until artifacts pass target-platform tests.

| SEC-002 | Installed software and licenses | No unapproved or improperly licensed software | Inventory alone cannot prove license validity; may require approved inventory/license source or custom check. |

**CP5 (2026-11-05):** SEC-008 effective local account aging, SEC-009 expiry warning and SEC-010 configured PAM complexity are integrated (§5.12). Configurable example: maximum 60/minimum 1/warning 10 days, length 14, four classes and at least one uppercase/lowercase/digit/special character. This supersedes the 7-day example. Existing v1/v2/v3 profiles gain no mandatory requirements; Ubuntu identity remains unsupported.

**Collection boundary resolved by operator:** trusted system `chage --list` may internally read shadow using existing privileges. BaradWatchU must not directly read shadow, request/extract/store hashes or log raw utility output. Retain only aging facts and ordinal IDs, no names/UIDs/home paths/dates. Landlock/read-only/no_new_privs remain mandatory; no elevation, unguarded fallback, account/PAM changes or privileged helper. Permission errors, unexpected formats and incomplete evidence are inconclusive (WARN with the sample policy). The [shadow implementation](https://github.com/shadow-maint/shadow/blob/master/src/chage.c) is the utility trust boundary; no claim that the subprocess cannot read hashes.

**Important:** SEC-011 is not mandatory for every employee. All controls, including built-ins, are individually assignable. A check disabled by policy is **SKIPPED/DISABLED**, not PASS and not a compliance failure; an inapplicable enabled check is **NOT_APPLICABLE** with rationale.

### 5.1 Check result states

- `PASS`: check executed successfully and verified its defined criterion.
- `FAIL`: check executed successfully and found a policy violation.
- `WARN`: completed observation is inconclusive or has unverified coverage/freshness; never a successful compliance result.
- `ERROR`: observation could not execute/parse safely (missing tool, permission, timeout, malformed output, unavailable read-only guard); never PASS.
- `UNKNOWN`: planned aggregate for undetermined outcomes in future policy/custom-check contracts. The Client observation report explicitly distinguishes WARN from ERROR; this is a separately versioned local observation contract, not an assertion that the future fleet schema is finalized.
- `NOT_APPLICABLE`: check is assigned but demonstrably inapplicable to the device/context.
- `SKIPPED`: conceptual state for disabled/excluded checks. CP2 records `enabled:false`, `status:null`, reason DISABLED_BY_POLICY in policy evaluation and omits unexecuted raw results; do not introduce a fabricated sixth observation status.
- Execution/transport errors must be recorded with structured reason codes; they must not silently become PASS.

### 5.2 Evidence requirements

Each result must include check ID, implementation type, check version, device identity, OS/platform details, policy version and digest, execution time, outcome, structured reason, collection method, privilege level and evidence metadata. Avoid secrets, full license keys, credentials and unnecessary personal data. Preserve evidence provenance and retention settings.

### 5.3 L1.1 / Checkpoint 1 — Standalone Audit Foundation

Explicitly authorized vertical slice, Client Rust only. Use reusable platform-neutral `Check` and report/result/evidence types; isolate OS detection and command execution in native adapters. Provide `baradwatchu-agent audit` (human) and `audit --format json`, preserving bootstrap/version/help. No Server/UI dependency, network calls, elevation, package/configuration changes, services, scheduling, custom checks, policy processing or extra checks.

- Stable IDs: `SYS-OS-001` OS identity, `SEC-001` pending RPM updates, `SEC-006` root block encryption. Descriptions and implementation versions accompany each result.
- Client observation schema `baradwatchu.audit-report.v1` is independent of product `0.0.1` and future shared fleet protocols. JSON includes agent version, OS/support details, integer UTC Unix-millisecond report/check timestamps, five exact states (`PASS`, `FAIL`, `WARN`, `ERROR`, `NOT_APPLICABLE`), structured reason/evidence/source/scope and deterministic counts. Device identity, policy versions/digests, signatures and ingestion are absent rather than invented; §5.2 remains the future complete contract.
- Parse `/etc/os-release` as data, fallback to `/usr/lib/os-release` only if missing; do not execute shell. Exact Fedora ID/numeric version qualifies; ID_LIKE derivatives, other platforms and image/ostree/Atomic Fedora do not. Identity may be observed successfully on an unsupported OS; Fedora probes then do not run, their results are NOT_APPLICABLE, and overall status is WARN. Identity read/parse failures are ERROR.
- Updates: fixed DNF5 cache-only `check-upgrade`, no plugins/refresh/transaction, no libsolv cache generation or persistent log output; DNF5 must support --skip-file-locks to avoid creating the system-repository lock. Existing persistent state remains readable but cannot be written; queries are not transaction-locked snapshots. Mandatory child-only Landlock ABI 3+ write/create/remove/rename/truncate restriction and no_new_privs; refuse unprotected execution if unavailable. Exit 100 => FAIL for observed pending updates; exit 0 => WARN/NO_CACHED_UPDATES (freshness/coverage unverified), missing cache/no repositories => WARN, missing tool/permissions/timeout/invalid command or execution/guard failures => ERROR. No update PASS in this checkpoint.
- Encryption: identify `/` using findmnt major:minor, trace all observed lsblk backing paths; PASS only for simple disk/partition/LVM paths each containing active dm-crypt directly backed by LUKS metadata. A proven plain root path => FAIL; unrelated LUKS is irrelevant. Btrfs, RAID/multipath, loop, overlay/network root, incomplete/conflicting metadata or unproven dm-crypt => WARN; tool/permission/parse/execution failures => ERROR. Scope excludes separate home, boot/EFI, swap, external drives and hardware/key-strength certification.
- Fixed native tool paths, minimal C-locale environment/no inherited secrets, null stdin, 30 s timeout and 256 KiB per output stream. No package lists, raw stderr, disk serials/UUIDs or repository URLs in reports. Local observations are not cryptographic proof against a compromised OS.
- Overall precedence ERROR > FAIL > WARN > PASS; skipped/inapplicable or empty coverage cannot create an overall PASS. CLI: 0 PASS/info/bootstrap, 1 execution failure, 2 invalid CLI, 3 FAIL without ERROR, 4 inconclusive/unsupported without ERROR/FAIL. Completed audits emit reports even with nonzero outcome codes; fatal clock/output errors can prevent a complete report.
- Gate: standalone CLI, three explainable structured checks, safe unsupported behavior, stable valid JSON, fixture-based domain/platform/command/error tests without root or real host configuration, fmt/tests/Clippy/debug/release builds. Real Fedora DNF5/storage smoke remains distinct from fixture evidence.

### 5.4 L1.1 / Checkpoint 2 — Audit Policies & Fedora Hardening

Authorized Client Rust extension of §5.3; preserve IDs, product version 0.0.1, bootstrap/help/version and report-v1 readability. No Server/Angular integration, new OS adapters/checks, services/scheduling, networking, elevation, authentication, remediation or dependency upgrades.

- **Observation / policy / evaluation:** native adapters produce typed facts; OS-independent policy evaluation borrows the report without modifying facts or evidence. Keep original report-v1 results/overall/summary and add optional typed observation plus `policyEvaluation` (`baradwatchu.policy-evaluation.v1`). CLI compliance/exit follows policy evaluation, which can differ from the legacy observation aggregate. Old reports deserialize; absent typed facts cannot prove PASS. Include the normalized policy and explicit enabled-mandatory scope, not invented policy authentication.
- **Strict policy contract:** regular UTF-8 JSON file ≤64 KiB; required `schemaVersion:baradwatchu.audit-policy.v1`; optional safe identifier and settings with strict defaults. Reject unknown/duplicate fields, check IDs, invalid values/types, zero age limits and unsupported versions before OS/clock/probe access. `policy validate FILE` executes no audit probes; `audit [--format json] [--policy FILE]` uses this layer. Sample: Client `policies/default.json`. SYS-OS-001 remains an unconditional diagnostic prerequisite.
- **Defaults / aggregation:** both SEC-001/SEC-006 enabled and mandatory; disabled probes do not execute. Informational checks retain visible FAIL/ERROR but do not gate mandatory compliance. All mandatory checks disabled or informational-only scope => WARN; unsupported OS cannot yield overall PASS. ERROR > FAIL > WARN > PASS. Missing/stale/inconclusive/unsupported evidence each configurable as WARN (default), FAIL or ERROR, never PASS/ALLOW. Probe failures remain ERROR. Observation maximum age defaults to 300 s, relative to report completion, with missing/future times inconclusive.
- **SEC-001:** DNF5 cache-only check-upgrade + enabled repo-info JSON + latest upgrade repoquery + applicable advisory-list JSON. Distinguish no pending, ordinary pending, security pending, unknown classification, missing/stale metadata and command errors. Positive advisory coverage is required to classify ordinary/security; absence of security advisories alone never proves ordinary. Applicable older security advisories still count if a newer candidate supersedes them. Ordinary/security actions independently FAIL (default), WARN or ALLOW. Unknown classification cannot PASS even with both allowed; a proven pending update may FAIL when both classes are disallowed, without asserting a vulnerability. Advisory counts are not CVE counts.
- **Metadata:** evaluate every enabled repo's reported timestamp and expiration interval; max metadata age defaults to 86400 s, still applied for expiry=-1. Missing/future timestamps, unknown coverage or repository include/exclude filters preclude PASS. Excludes are ignored only for query execution to prevent hiding pending packages; configuration is not rewritten. Scope is configured enabled repositories and DNF active modular streams, not proof of upstream completeness/current vulnerability freedom. Source metadata timestamps do not prove last package installation or live network freshness. No refresh is allowed. Multiple bounded queries are not an atomic transaction snapshot.
- **SEC-006:** cross-check all root lsblk ancestry edges with independent kernel sysfs slave/partition ancestry and active dm LUKS identity; adjacent LUKS metadata is required. Support simple LUKS, LVM on LUKS, LUKS on LVM and multiple backing paths only when the complete graph is established. Default LUKS requirement passes only if all verified paths are protected; known plaintext paths FAIL. Explicit NOT_REQUIRED permits known plaintext but never ambiguous topology. Btrfs, RAID/multipath, unknown device-mapper, loop/overlay/network root, inconsistent or missing chains remain inconclusive. Scope remains root only, not swap/home/boot, other partitions or key strength. Do not report UUID values.
- **Safety / prerequisites:** conventional Fedora RPM/DNF5 with the required JSON/query flags, util-linux findmnt/lsblk, readable sysfs/dm metadata and existing repository cache. Retain §5.3 bounded commands, clean environment, no plugins/log/cache writes/system lock creation, mandatory Landlock ABI≥3/no_new_privs and no unsafe retry. No transaction, configuration mutation, metadata refresh, privilege escalation or network request is introduced. No weakened TLS or dependency substitutions.
- **CLI codes:** 0 mandatory policy PASS or informational commands/valid policy; 1 mandatory ERROR (probe or policy evidence handling) or fatal audit/output failure; 2 invalid CLI/policy; 3 mandatory FAIL without ERROR; 4 WARN/unsupported/no mandatory coverage without ERROR/FAIL. Informational ERROR remains visible without changing mandatory compliance exit. Completed audits emit reports even on nonzero outcome codes.
- **Gate:** strict policies validate/apply without probes on malformed input; raw observations remain unchanged; update classes use positive evidence; root encryption requires complete backing topology; unknown never PASS; deterministic offline tests cover schema, aggregation, classifications/freshness, storage, permissions/tools, unsupported systems, JSON compatibility and Landlock failures. Required fmt/tests/Clippy-with-denied-warnings/release build must pass. Real Fedora execution must be reported independently from fixture validation; no automatic CP3 progression.

### 5.5 L1.1 / Checkpoint 3 — Arch Linux Adapter

Native Arch support is explicitly authorized now; this does not authorize the wider L2 matrix. CP2 implements the local observation/policy/evaluation separation in §5.4; CP4 adds explicit local v2 controls in §5.6. The server trust, assignment, signing, caching and drift mechanisms below remain future requirements. A local policy file is not an applied server-authorized policy.

- **Desired Policy:** versioned policy assigned by the server to device/group; controls enabled/disabled, parameters, platform constraints and custom-check manifest digests.
- **Applied Policy:** last server-authorized policy validated and stored by the agent, including signature, version and digest.
- **Observed State:** audit outcomes produced against a specific applied policy and check implementation versions.
- Server compares desired/applied versions and digests; mismatches are `POLICY_DRIFT` and must not be silently certified compliant with the new policy.
- A client can audit offline against its last trusted policy, reporting its age and whether it is stale; the server decides whether such results satisfy current reporting rules.
- Assignment precedence (global → group → device), group membership, exception approval and conflict resolution must be defined in L0.
- Server can disable any built-in or custom check for a device/group; local users cannot silently override server-required checks.
- Local policy files must have OS-appropriate integrity/access protections. Signed policy alone does not prevent a fully privileged local attacker from tampering with runtime behavior.

### 6.2 Custom Security Checks (AQTRunCat-style extensibility)

- Built-in checks ship with the agent; custom checks are external scripts/executables with the **same result schema**.
- Custom checks may be implemented in Bash, PowerShell, Python or native binaries where the target OS supports their runtime.
- A custom check is executable only when **(a)** the server policy assigns/enables its ID, **(b)** the client has the locally registered artifact, **(c)** ID/version/content digest and authorized manifest match, **(d)** platform and execution permissions match.
- The server may register and assign metadata but **must not push arbitrary executable content for immediate execution** in the initial design.
- Custom artifacts are installed/approved locally by an administrator through an explicit trusted procedure. Automated distribution, if ever supported, requires a separate reviewed signing/approval model.
- Run custom checks unprivileged by default, with bounded timeout, output size, resource limits, working directory and restricted access to secrets; sandboxing should be implemented where supported. A script must not inherit the agent's private key or server credentials.
- A custom check must not call the privileged helper as a generic shell bridge. Any privileged inspection requires a separately implemented and authorized typed operation.
- Missing/mismatched custom artifact results in `UNKNOWN` with reason such as `CHECK_NOT_INSTALLED`, `DIGEST_MISMATCH`, `UNSUPPORTED_PLATFORM`, `TIMEOUT` or `EXECUTION_ERROR`, and an explicit configuration/coverage issue.
- Script output is treated as lower-trust evidence than a native trusted probe; the report must indicate provenance and limitations.
- Example: `CUSTOM-INTELLIJ-LICENSE` on workstation X checks installation and licensing status. Merely finding the `idea` executable **does not prove license validity**; a genuine license verification method must be supplied by the check author.

### 6.3 Illustrative custom-check manifest

```json
{
  "id": "CUSTOM-INTELLIJ-LICENSE",
  "version": "1.0.0",
  "platforms": ["linux"],
  "entrypoint": "controllo_intellij.sh",
  "sha256": "<actual-artifact-sha256>",
```

## 7. Trust, enrollment and privileged operations

### 7.1 Enrollment

- First installation requires an authorized administrative enrollment step; USB/offline bootstrap is a supported candidate, not mandatory for all deployments.
- Prefer one-time short-lived enrollment credentials; **never distribute the server/CA private signing key to clients**.
- Each endpoint generates its own keypair locally; use TPM, OS key store or secure enclave protection where available. Server registers device identity and public key/certificate.
- Authenticate communications (TLS, preferably mTLS or equivalent per-device credentials); provide revocation, rotation and lost-device recovery.
- Cryptographic authorization does **not** itself grant root/admin privileges; OS permissions and installed privileged components do.

### 7.2 Privilege boundaries

- The long-running agent should be non-privileged wherever feasible.
- L0/L1 must measure which checks are feasible without elevation on each platform. Insufficient privileges produce ERROR in Checkpoint 1 (UNKNOWN remains a future aggregate), never PASS.
- If required, use a separately authenticated and tightly scoped privileged helper. Never expose arbitrary shell, unrestricted process execution, arbitrary file write or arbitrary command-line flags through the helper.
- Helper verifies caller identity, typed operation, arguments, authorization, expiration, target device, replay protection and local constraints independently.
- Remediation commands must be explicitly implemented and allowlisted; signed server instructions do not bypass these checks.
- Remediation must support approval policy, dry-run where meaningful, audit trail, bounded execution, post-action audit and rollback/recovery where feasible.

### 7.3 Candidate future remediation operations (L3, not L1)

`SET_SCREEN_LOCK_TIMEOUT`, `CONFIGURE_APPROVED_DNS`, `CONFIGURE_PASSWORD_POLICY`, `START_OS_UPDATES`, `RESTART_APPROVED_SERVICE`, `CONFIGURE_BROWSER_POLICY`. Each requires platform-specific safety analysis; high-impact changes may need local user/admin approval or a maintenance window.

### 7.4 Client Milestone 1 — Cryptographic identity & trust store (operator goal 2026-11-10; implemented on the Client 2026-11-10)

Principle: **trust never comes from the network.** Public keys are exchanged beforehand through verified external channels and imported locally; identity generation is always voluntary and manual. Scope is local only: no listener, discovery, Client/Server connection, TLS/handshake, network pairing, TOFU, remote audit or remediation, privileged service.

- **Identity:** one Ed25519 key pair per installation (`ed25519-dalek` 2.x, seed from the OS CSPRNG via `getrandom`). Generated only by `identity generate` / dashboard «Genera identità» after the mandatory confirmation text; never at install, start-up, audit or update; never regenerated when files are missing/corrupt (status DAMAGED, recovery = explicit full reset). Absence is not an error: local audits, dashboard, history and PDF are unaffected. A second generation is refused and points to the reset.
- **Formats (interop with the future Server):** fingerprint `SHA256:` + 64 lowercase hex of SHA-256(raw 32-byte public key); Device ID `BWU-XXXX-XXXX-XXXX-XXXX` = first 64 bits of SHA-256(`baradwatchu.device-id.v1\0` ‖ key); Server ID `SRV-…` same with `baradwatchu.server-id.v1\0`. Public file `baradwatchu.public-identity.v1` `{schemaVersion, role client|server, id?, name?, algorithm Ed25519, publicKey (std base64), fingerprint?, createdAtUnixMs?}`, unknown fields refused, declared id/fingerprint recomputed. The future Server must export its key in this format with `role: "server"`.
- **Storage:** `state_home()/identity/` (Linux `~/.local/state/baradwatchu/identity`, Windows `%LOCALAPPDATA%\baradwatchu\state\identity`, non-roaming): `state.json` commit pointer, immutable `key-<hex>/{public.json,private.key}` and `trust-<hex>.json`. Copy-on-write + atomic `state.json` rename under an exclusive lock = transactional reset/trust changes; unreferenced artifacts are garbage-collected by the same or next change; missing/corrupt state with artifacts present ⇒ DAMAGED, nothing deleted or adopted. Permissions: Unix 0700/0600, verified at every use (signing refused if too open); Windows protected DACL (user + SYSTEM) set at creation, not re-verified.
- **Private key:** never displayed, copied, exported, returned by local APIs, or written to logs/audits/PDF/notifications. Limits accepted for this milestone: same-user processes, administrators/root, backups and endpoint compromise; no physical-erasure guarantee for retired keys (SSD/CoW/snapshots/backups). No TPM/Secure Enclave/OS key store (possible later).
- **Trust store:** independent of the identity (imports work without one). Entry = serverId, name, Ed25519 key, fingerprint, importedAt, TRUSTED|REVOKED (+revokedAt). Import only from a local file (CLI `trust import FILE`, dashboard file picker) after showing name/ID/fingerprint and an explicit confirmation (CLI interactive "yes" or `--fingerprint` with the verified value; dashboard checkbox + server-side check that the confirmed fingerprint matches the file). Refused: malformed/weak keys, client identities, own key, duplicates, revoked keys, a trusted name already in use, >256 entries. Revocation keeps the record; only «Rimuovi tutti i Server trusted» (`trust clear`) forgets revocations. `trust clear` keeps keys, Device ID and fingerprint.
- **Full reset** (`identity reset`, typed `RESET` confirmation, `--yes` for scripts): new key pair + empty trust store in one commit, pending consent requests expired; out-of-band exchange must be repeated.
- **Contract for future remote audits (decision):** even a trusted Server must obtain the user's acceptance through the local notification/consent flow before any remote audit. Trust only allows a Server to *present* a request. `identity::check_remote_request` returns at best `RequiresLocalConsent` (no variant authorizes execution); unknown ⇒ `UnknownServer`, revoked ⇒ `RevokedServer`, bad signature ⇒ `InvalidSignature`. Trust is matched on the full presented key proved by a signature, never on name, IP or declared ID. The existing consent model (`consent.rs`) is the component to reuse.
- **Local API:** dashboard loopback bridge only (session token, Host, Origin, JSON content type); changes require body `{"confirm":true}` (import: `confirmFingerprint`). Not a remote interface.
- **Verified 2026-11-10 (Arch):** `cargo test --workspace --locked` 111 tests (17 identity + 1 dashboard HTTP-guard + 2 CLI integration new), fmt, Clippy `-D warnings` (Linux; plus cross Clippy `x86_64-pc-windows-msvc` and `aarch64-apple-darwin`, compile/lint only), Angular build + npm test 4/4, live isolated dashboard driven by headless Chrome (generate, hidden key + copy, import preview/confirm, reset dialog cancel). Not run on Windows or macOS.

### 7.5 Client Milestone 2 — Persistent agent & trusted Server communication (operator goal 2026-11-10; implemented on the Client 2026-11-10, Linux only verified)

Principle unchanged: **a trusted Server can request an audit, never run one without the user's explicit local acceptance.** Server application out of scope (protocol + test harness only).

- **Architecture (analysis alternative B, minimal):** same executable. `baradwatchu-agent service run` = system service (root/LocalSystem; systemd `baradwatchu-agent.service`, LaunchDaemon `io.baradwatchu.agent`, Windows service `BaradWatchU`; OS restart on failure): mTLS listener, availability/BUSY/UNAVAILABLE, request records; never audits, never writes in user folders. `remote link` = per-user agent started/restarted by the tray (stdin pipe ⇒ dies with the tray): consent + existing `run_audit` as the user. No broker/framework.
- **Identity per user (operator decision 2026-11-10, option «service uses the user key»):** no service key, no new keys, no migration. User runs `remote enable` ⇒ IPC registration (peer account from the OS, not from data) of their own identity folder; service reads that user's key + trust store (owner/mode checked on opened handles, links refused, no lock taken) for SNI = Device ID. Several users per PC possible. Identity reset ⇒ registration stale until `remote enable` again. Known consequence: privileged process uses user keys; encrypted/unmounted homes ⇒ unreachable (no UNAVAILABLE answer).
- **Transport:** TLS 1.3 only, RFC 7250 raw Ed25519 public keys both sides (rustls 0.23 + ring), scheme ed25519 only, no resumption/tickets. TLS key = M1 identity key = trust-store key (no X.509/CA/second chain). Client verifier: key TRUSTED by some registration at handshake, then exact match for the SNI user. Requester helper `remote::tls::requester_config`.
- **Remote API v1** (`docs/remote-protocol.md`): `POST /v1/audit-requests` {schemaVersion `baradwatchu.remote-audit-request.v1`, requestId 8–64 `[A-Za-z0-9._-]`, operation `AUDIT_REPORT`, issuedAtUnixMs ±5 min}; `GET /v1/audit-requests/{id}`; `GET …/{id}/result`. States PENDING_CONSENT, RUNNING, COMPLETED, REJECTED, EXPIRED, BUSY, UNAVAILABLE, FAILED (+reason). Async polling, one request per connection. Duplicate requestId ⇒ stored status, never re-executed; BUSY/UNAVAILABLE not stored (retry same id). Records kept 24 h on disk (no results); results in memory 1 h. Only requesting Server (key) sees its requests.
- **Availability/concurrency:** no linked session or tray ⇒ UNAVAILABLE; screen lock not detected by design (request waits, 120 s from prompt); pending consent or any audit (non-blocking `state_home/.audit.lock`, also taken by CLI/dashboard audits) ⇒ immediate BUSY, no queue; service allows one active remote request.
- **Revocation/reset:** `trust revoke`/`trust clear`/`identity reset` expire pending remote consent (`consent::expire_remote_pending`); next connection fails handshake; trust re-checked after acceptance.
- **Off by default:** listener only with admin-written `service.json` `{schemaVersion baradwatchu.service-config.v1, remote.listen ADDRESS:PORT}`; registration only after manual identity generation; installers never generate keys/open ports; firewall manual/IT. **Installation (operator 2026-11-10): single entry point; the service is part of the Client.** Two modes: *system* (standard: Linux root-owned prefix, default `/usr/local`; Windows setup for all users, its default) = agent, dashboard, tray and system service (remote mTLS API), always installed/updated/removed together (`install.sh` in its sudo step via `packaging/service/install-service.sh`; setup via `install-service.ps1`); *per user* (`--local`/user-writable prefix, `install.ps1`, setup "only for me") = all local features without admin rights, no service, no remote communication, kept fully supported for development/tests/diagnostics; no per-user service. Service stopped before files change, restarted and verified on the new executable, restarted after a failed install; another installation's service is never taken over. macOS: no Client installer yet (script by hand). User identities, trust stores, history and `/var/lib/baradwatchu` always kept; no key generation, listener off, firewall untouched. Dashboard API stays a user process on loopback (M2 architecture unchanged).
- **Verified 2026-11-10 (Arch, dev user, not root):** 126 tests + 1 real-time 120 s test; `tests/remote_service.rs` covers all §13 scenarios of the goal with the real binaries and a Server harness; tray spawns/stops `remote link`; unit syntax `systemd-analyze verify`; cross Clippy Windows MSVC workspace and macOS agent (ring compiled against stub headers, type-check only). Windows/macOS service, pipe, ACL owner check, launchd: not run.

## 9. Non-functional requirements

- **NFR-SEC:** secure defaults, least privilege, no arbitrary remote execution, protected credentials, authenticated IPC, signed policies and immutable/tamper-evident server audit history where feasible.
- **NFR-PRIV:** collect minimum device/user data necessary for compliance; configurable retention, redaction and access control. No passwords or full license secrets in reports.
- **NFR-PORT:** architecture supports Linux/Windows/macOS; OS-specific checks must report unsupported features honestly.
- **NFR-REL:** offline audits continue despite network outage; buffered results sync later with idempotency and bounded local storage.
- **NFR-OBS:** structured logs, correlation IDs, check duration and actionable errors without leaking secrets.
- **NFR-EXT:** checks are modular, versioned and testable independently; custom checks never modify core binaries.
- **NFR-PERF:** background operation must avoid disruptive CPU, disk, network or battery usage; concrete resource budgets established by benchmark during L1.
- **NFR-COMPAT:** explicit support matrix for OS versions, architectures and security APIs; support boundaries are documented and tested.
- **NFR-TEST:** automated unit, contract and integration tests; test doubles must not be misrepresented as real OS compliance results.
- **NFR-DEPLOY:** server can run on-premises on Linux without mandatory third-party cloud services.
